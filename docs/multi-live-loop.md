# 多人演出自动打歌循环

入口：项目根目录的 `run_multi_live.cmd`，或 `.conda/python.exe tools/run_multi_live.py`。

先只查看计划（不会连接窗口或发送输入）：

```powershell
.\run_multi_live.cmd --rounds 3
```

明确允许真实输入后运行：

```powershell
.\run_multi_live.cmd --rounds 3 --live
```

先打开唯一的 `hololive-Dreams` 窗口，停在游戏主世界或演出入口；可以在终端或聊天窗口输入启动命令。
带 `--live` 启动后会自动恢复并激活游戏窗口，最多尝试三次；连续两次观察确认游戏在前台后，才开始截图识别和游戏输入。
无法获取焦点时记录 `startup_focus_failed`，不会直接进入流程。只看计划和离线图片识别均不切换焦点。
运行期间按 F12 停止。启动成功后的失焦、最小化、位置/尺寸变化仍会在输入检查时停止，不会自动抢回焦点。
请先停止其他游戏自动操作程序。本入口的进程锁防止重复开启本入口，不能替其他旧脚本提供互斥。

## 流程

Pickup提交后，设置决定优先通过底部难度标签和当前启用的决定按钮确认，不等待顶部标题稳定；
仅需两帧目标稳定，允许2px位置抖动。设置决定每局最多3次、重试间隔2秒，仍不操作等候室的决定成员。
运行state事件保存识别依据evidence与局部匹配scores，便于排查等待发生在页面识别还是按钮启用阶段。

首音符/Pickup修复：选曲页只点击Pickup，不点击旁边的“决定”。通用勾号不作为选中状态；
缺失或置灰时等待，丢首击时限次重试Pickup；“决定”只用于后续难度设置页。
首个新鲜音符帧每曲额外触发一次“释放六键 → 当前抬键间隔 → 重新按下请求”，原250ms恢复防误触检查保留，
后续音符不重复执行。控制台显示首音符重按请求，events.jsonl记录释放、恢复请求及暂缓的危险列。

演出 → Live Portal/MULTI → GRADE → 等候室（绝不点决定成员）→ Pickup自动选择高得分歌曲并提交 → 等待后续选曲/难度页 → 沿用当前难度/队伍/AUTO设置决定 → 立即初始化原打歌引擎 → 加载期间不输入 → 演奏HUD确认后默认六键常按 → 确认结算 → 停调度并释放按键 → 下一步/GET/达成奖励/个人成绩/分数奖励/成员EXP/活动奖励 → 续玩选择。

Pickup是自动选歌提交动作，不是给“决定”用的状态开关。识别只依赖Pickup和选曲页标题锚点，
不依赖旁边“决定”按钮是否存在、点亮或匹配成功。提交后重新观察游戏自动推进；
同一选曲页且按钮仍可用时才间隔重试，每局总共最多三次，动画/置灰变化不重置预算。
事件pickup_requested记录语义及尝试次数；它只表示输入请求，后续页面才是推进证据。

点击设置“决定”后即调用引擎，不等待音符。采集适配器在SCORE/LIFE/键位HUD连续确认前不给调度器提供图像，
因此加载/淡入/菜单期间不会误按。HUD出现后无需F8，按原all-held逻辑建立六键基础持键，继续受原恢复防误触保护。
“决定”首次输入丢失、两秒后同一启用按钮仍在时，先清理引擎，再返回菜单按原三次预算重试。

多人等人和其他人选曲阶段只有等待。
每次点击重新观察：同一菜单按钮仍启用且页面未推进，间隔至少2秒，最多3次。新奖励层重新获得独立预算。
变化后的未知页面按需开启OCR。只推进登记奖励标题下有按钮关联和启用颜色证据的“确定/继续/下一步/下一波/OK/关闭”，
叉号还受登记弹窗位置约束；无法确认语义或启用状态则超时停机，保留现场。

演奏中没有菜单截图线程或菜单输入；曲终检测复用引擎 diagnostics 的同帧图像，最多5Hz局部模板检查。
两次独立采集均命中成对结算特征才请求 `should_yield`。休止和空谱面不能作为曲终。
同步等待引擎返回，检查 `cleanup_error` 和调度线程退出后才让菜单接管。松键失败不继续菜单。

目标局数只在本脚本启动并打完的歌曲观察到结算后加一；奖励弹层不加局数。
达到目标后继续结算收尾，停在“要继续玩吗”页；不会选择“玩同一个游戏”，也不猜测最终退出动作。

## 参数、配置和日志

- `--rounds N`：必填，1..1000。
- `--timeout 7200`：会话安全上限，秒，包含等待和演奏。
- `--song-timeout 1800`：单曲安全上限，秒。外部取消不改原引擎 timeout 配置。
- `--matching-timeout 600`：等人时间预算，秒。
- `--config 路径`：可选现有音游JSON。只读，不覆盖用户参数；不自动读取或执行调参CMD中的参数。
- `--rhythm-profile mechanism|tuning|config`：默认`mechanism`，读取现有调参CMD的数值及机关关闭入口的shadow/off开关；
  `tuning`仅读调参CMD；`config`仅读JSON。显式指定`--config`且未指定profile时默认`config`。
- `--inspect-image 路径`：只离线识别一张截图，与 `--live` 互斥。

基础几何沿用 `domains/hololive_dreams/models/rhythm/rhythm_game_config.json`，默认将`run_rhythm_tuning.cmd`和
`run_rhythm_mechanism_test.cmd`的现有有效参数传给引擎：当前为all-held、offset75ms、网格20ms、抬键提前5ms、
global_flow/measure_clock=shadow、mechanism_mode=off。每次启动读取，不复制一套调参值，不执行带pause的CMD。
启动打印并在events.jsonl的rhythm_settings事件保存完整有效配置及来源。不改原引擎、调参CMD、JSON、游戏AUTO或难度。
同帧曲终识别要求全客户区 ROI `[0,0,1,1]`，不满足时实机入口报错，要求用户选用全区配置，不会自动改写。

日志复用现有 DailyJournal，放在 `runtime/daily-tasks/<本次目录>`：`events.jsonl` 记录页面、输入重试、控制权和计局证据，
`inputs.jsonl` 记录菜单输入，`result.json` 保存完成/停止原因。菜单停止时保存 `stopped-frame.png`。
不会自动录制整曲；引擎现有输入审计仍使用原路径。

## 验证范围

启动焦点修复新增8项离线回归，与24项循环回归共32项通过：终端启动自动激活、异步前台确认、最小化恢复、
已在前台零切换、激活失败三次上限、句柄消失、取消、只看计划/图片识别不抢焦点。

新增24项离线回归，连同公共交互、无限时引擎/松键和连续升级奖励测试，共60项通过。
涵盖16张用户原图、80%尺寸与桌面坐标映射、动态角色/分数反例、加载/等人非结算、置灰按钮、首次点击丢失、
OCR延迟弹窗、三局不启动第四局、连续多层奖励、停止、清理失败及真实引擎模拟截图交接。

参数/早启动修复新增11项回归，与循环及焦点测试共43项通过，包含真实引擎在无音符模拟画面上六键DOWN/UP和菜单误判反例。
没有真实游戏按键测试；原图的识别回归不等于全分辨率、动画过渡和实机命中率验证。
起曲门控使用已归档演奏HUD，不再等待音符；参考来源见domains/hololive_dreams/data/multi_live/README.md，仍需实机验证起曲时机。
当前音符流速/间隔算法仍在另行排查；脚本不会声称算法完全稳定或游戏Perfect。
体力不足、错误或断线停止，不购买、不补体力、不自动重连。
