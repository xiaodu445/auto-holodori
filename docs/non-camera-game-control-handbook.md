# 非视角游戏控制经验手册

版本：2026-10-17。案例：hololive Dreams“进入强欲之牌”。用途：将截图驱动的菜单、地图、弹层、交互和模块交接经验沉淀为可复用工程方法。

“非视角”指主要通过界面状态与键鼠交互完成流程，不涉及自由旋转镜头、三维路径规划和连续追踪导航。案例中的短按W作为已知路线段保留，复杂移动另见 [自由场景导航设计](free-world-navigation-plan.md)。

证据范围：本文依据用户确认规则、项目源码、失败日志和离线测试整理。“通用方法”是可借鉴的设计模式；“当前实现”是代码实际行为；离线通过不代表所有实机条件已通过。这里没有训练出能理解任意游戏画面的模型。

## 1. 先定义模块成功条件

入口模块的目标：进入实际High & Low准备页，返回成功，并释放全部输入。它不负责下注、玩法、收益判断或退出游戏。

成功证据：实际小游戏页面的标识与准备控件组合，不能只因地图详情里出现High & Low、按键发送成功或目标名称出现就结束。

结果携带module、outcome、verified、ui_state、flow_step、verification、next_module与trace_directory等信息；不同退出分支字段尚未完全统一，调用方应使用get读取。next_module是建议接管方，不代表自动执行授权。unknown表示未能确认，不等于游戏失败。

可复用经验：每个操作模块应有明确的进入条件、完成证据、停止条件和返回契约。多个模块通过实际可观察的界面衔接，避免依赖“上一模块大概点成功了”。

## 2. 从世界规则到可执行流程

用户确认的正常路线：

自由场景 → M地图 → 电玩巨蛋城 → 游玩区域 → 赌场右侧小游戏 → 地点详情确认强欲之牌 → 移动 → 等传送 → 短W靠近 → 猜高低交互 → 可选对话 → 实际准备页。

替代路径：

- 已在目标详情：直接移动，跳过地图图标选择。
- 已在交互提示：直接交互，跳过靠近。
- 已在对话：推进对话，跳过重新选设施。
- 已在准备页：验证后直接返回成功。
- 已识别为游戏区：经大厅操纵杆切换赌场，再重新导航。
- 地图过大/偏移：整理视野后再找图标。
- 错误小游戏详情：返回上一层，重新选择，不盲传送。

操纵杆：地图详情移动到面前，E交互；滚轮仅移动旁边指示标记，E执行所指选项；Alt点击选项直接执行。区域保留上次选择。“切换为游戏区”描述目标区域，可作为当前可能已处赌场的线索。

当前限制：地图配色判定赌场/游戏区仍未完整落实；只有已支持文字或模板证据才进入相应路径。地图名称缺失也可能需要OCR。不能将上述理想路线描述成所有起点均可自动处理。

## 3. 区分三种状态

| 概念 | 回答的问题 | 例子 |
|---|---|---|
| 界面状态ui_state | 当前帧实际呈现什么 | map.location_detail、dialogue |
| 流程步骤flow_step | 这个模块准备执行什么 | teleport、arrived、interact |
| 预期结果expected_ui_states | 动作后优先检查什么 | dialogue、minigame.greed.ready |

错误示例：历史上执行过interact，于是后续任何画面都当作“等待游戏”。

正确思路：历史只提供检查优先级；本次画面出现交互提示，就承认交互提示仍然存在。对话结束后提示重新出现时允许受限恢复，不被旧步骤锁死。

当前entry_contract记录预期结果用于日志和解释，尚不是完整、严格校验每条转换的通用状态图执行引擎。状态分类器与入口执行器已分离，其他模块尚未全部迁移。

## 4. 观察顺序：便宜证据先行

建议链路：

截图一次 → 结构锚点 → 候选界面 → 目标局部匹配 → 决策 → 输入 → 新帧确认。

知识匹配日志中的knowledge是图标模板匹配，不是读取知识文档。原先每个模板扫完整窗口，几百毫秒会累积成明显延迟。

当前入口使用：
- 轻量结构扫描，输出world_features。
- 根据当前结构与流程预期选择模板分组及区域。
- 明确对话/奖励/升级时跳过knowledge扫描。
- 连续无法形成可用决策约2秒后扩大模板搜索。
- 持续未知约5秒，且距上次OCR至少5秒，才调用OCR；UIA仍关闭。

OCR兜底当前仍是游戏窗口OCR，尚非所有页面的精确局部OCR。已识别结构但缺少具体目标，也可能需要OCR。

预判的正确用途是减少搜索范围，不是代替观察。未知画面不能被随意归类为加载，也不能被自动学习成可点击目标。

## 5. 选择真正稳定的视觉特征

### 自由场景

人物、服装、镜头朝向、地点、光照都变化，不能比较整张世界画面。

可用证据：顶部多个HUD图标、左下相机、右下跳跃等布局关系。当前既保留文字小块证据，也增加至少三个位置一致图标配合独立世界按钮的路径。孤立图标或单个相似点不足以证明自由状态。

### 对话

曾经错误地裁剪具体台词“为了抓住机会”并绑定Shiori。换成佩克拉、换一句话，立即失效。

当前通用特征：底部E键提示与推进三角组合。NPC头顶世界气泡不等于正式对话。角色与台词是动态内容，推进控件和布局才是稳定结构。

### 地图及详情

地图页以定位针、MAP标记、标题布局识别。地点详情由特定内容加移动按钮形成组合，不强制所有模板同时命中。详情面板比背景地图优先。

当前强欲之牌详情模板与移动模板同时命中，即使地图名模板漏掉，也可识别为地点详情；传送仍依赖目标名称确认，不能任意同图标就移动。

### 奖励、升级与选项

GET标题配合青色色带；RANK UP标题配合下部色带；交互选项配合侧方小鼠标及E提示。奖励种类、角色、数值、日期不作为长期固定模板。

覆盖层优先于背景HUD：奖励页或对话页可能仍能看见菜单和顶部图标。看到背景HUD不代表恢复操作。

## 6. 特征资产管理与前景蒙版

当前通用状态特征在data/ui_features中独立存储：20个裁剪，七个世界按钮/图标附前景图与蒙版。manifest保留来源截图、裁剪框、搜索区域、来源SHA256。运行时不再现场从整张归档图裁剪。

另有data/template_sources/in_game/entry中的入口目标模板，以及vision_library注册资产。状态资产与具体点击目标资产用途不同。

前景蒙版经验：
- 裁剪要围绕稳定符号，尽量排除动态背景和提醒标记。
- 白/黄UI可提取颜色前景，配窄背景边界作约束。
- 光亮背景容易产生虚假的高相关峰值；当前前景匹配使用带蒙版的归一化平方差。
- 多个锚点联合、位置关系及独立区域支持，比单个分数更重要。
- 一个偏离行的匹配不能使所有其他有效锚点一起失败；采用一致证据子集。
- 阈值是经验门槛，不是“识别正确概率”。

目前蒙版仍有颜色假设，亮度极端变化、UI换肤、遮挡或缩放仍可能失效。不要把一套白黄阈值宣称为全游戏通用特征提取器。

## 7. 坐标、区域和尺度

限定区域搜索不是固定点点击：顶部图标在顶部区域搜索，对话在底部，移动按钮在右侧详情区域搜索。

四种坐标应明确区分：原截图像素、窗口相对坐标、归一化布局、最终桌面物理坐标。裁剪匹配必须加回ROI原点与窗口原点。不要从历史日志取旧坐标点击。

当前结构扫描按宽度归一化并保持比例，候选尺度小幅变化；设施图标受地图缩放影响更大，只为地图设施增加少量尺度，不让所有模板无限多尺度扫描。

窗口目标1280×764是参考外框，不是精确客户区。当前宽±20、高±10范围可直接使用；尺寸调整不生效不应仅因尺寸差异中止流程。窗口消失、边界无法读取、失焦或遮挡另行处理，不能用宽容尺寸规则掩盖这些问题。

## 8. 地图视野恢复

曾经出现：地图放大、偏移，目标在屏幕外；程序反复点游玩区域，毫无进展。

当前策略：
1. 如需先选择游玩区域，只做一次。
2. 无目标时检测右下红色圆滑块及水平轨道，必须双证据，不按固定比例盲点。
3. Alt拖滑块到轨道左端，最多两次，每次重观察。
4. 仍缺目标时最多两次有限平移地图，之后返回map_target_missing。
5. 地点详情已打开时不操作背景地图。

缩放可能改变图标大小，因此视野恢复与设施多尺度匹配必须成套处理。当前平移是有界恢复动作，不是几何全地图覆盖搜索；不保证能把任意偏移的地图重居中。真实拖动与小图标泛化仍需运行验证。

## 9. 动作、延迟与等待

游戏实际输入规则也是识别系统的一部分：Alt释放指针；E交互；M只打开地图；Esc一般返回当前层但不用于对话。忽略这些规则会出现“识别正确、操作无效”。

动作成功只证明输入已派发。点击移动后必须看传送/到达，交互后必须看对话/小游戏。推进一次后重新观察，不把两种弹层合成无反馈双击。

不要用“两轮未知”当超时。识别速度越快，两轮越短，动画还没结束就误触发异常。用单调时钟记录等待起点、重试间隔和总时限。

当前入口默认整体300秒、等待推进30秒、非等待步骤最多三次输入；W短按0.3秒、两次预算保持用户认可的原设置。拖动后及正常动作后仍有等待，当前不是高频实时控制系统。

典型动画用户经验约1秒、慢时约5秒，不是游戏保证。长期无法确认时返回具体缺失证据和最后动作，而非宣称“游戏失败”。已知加载积极等候，明确错误不靠无限等待解决。

## 10. 故障复盘

| 实际问题 | 原因 | 采用的修正 |
|---|---|---|
| 1280×757或1298×767被拒绝 | 把参考尺寸当绝对条件 | 双轴容差、非致命尺寸警告 |
| MAP和正确地图名都有却unknown | 强制要求map1/map2也命中 | 标题/结构确认与目标定位分开 |
| 详情被识别为现场猜高低 | 地图名漏匹配使状态降级 | 详情内容＋移动组合优先 |
| 换角色后对话卡死 | 台词和人名过拟合 | 底部E＋推进三角 |
| 世界背景变化导致unknown | 裁剪混入背景，单行证据过严 | 前景蒙版、多区域、离群点容忍 |
| knowledge约400～600ms | 多模板全窗口扫描 | 结构路由、局部ROI、明确弹层跳过 |
| 对话后提示恢复却一直await_game | 历史标记锁定等待 | 已经历对话后允许受限reinteract |
| 地图目标不在视野 | 只重复区域点击 | 缩小、有限平移、重观察 |
| 上次失败无法复盘 | 只有最终结果、动作名 | 每次运行独立trace保存证据和参数 |
| 模板测试通过仍实机失败 | 来源图自匹配被误当泛化 | 未参与模板构建的截图、反例及变换测试 |

## 11. 可维护的模块组织

- perception：截图、OCR、通用模板算法。
- domains/hololive_dreams/visual_features.py：稳定锚点扫描。
- states.py：纯界面分类与证据。
- entry_search.py、templates.py：模板分组与局部搜索。
- entry_observer.py：观察调度与OCR兜底。
- entry_contract.py：动作预期说明。
- entry_flow.py：强欲之牌具体流程及恢复。
- map_view.py：地图滑块检测。
- trace.py：按次归档。
- 旧models/greed_cards_entry.py保留兼容加载。

迁移采用渐进方式。不要为统一名称一次重写所有成熟模块，也不要只加公共枚举却继续在每个模块独立猜页面。真正统一需要共同消费结构证据、共享语义和一致日志。

## 12. 日志与验证方法

runtime/greed-entry/<时间-ID>/events.jsonl逐次记录：
- 当前帧窗口信息、OCR/模板结果及耗时。
- world_features锚点分数、范围及搜索模式。
- ui_state、flow_step、expected_ui_states。
- 输入名称、参数、执行结果、异常和最终结果。

result.json保存本次返回。当前没有完整逐帧像素截图或视频，文字证据无法还原所有视觉错误。后续可增加失败前后环形截图缓冲，但尚未实现。

验证至少包含：
1. 模板源图匹配，用于确认资产没裁坏。
2. 不同背景、角色、台词的独立样本。
3. 对话、菜单、奖励等背景HUD反例。
4. 缩放、亮度、窗口原点变化。
5. 模拟流程、超时、取消、输入释放、旧命令兼容。
6. 最终真实游戏跑通，单独记录验证版本与起点。

最近相关83项离线测试通过；不是全项目测试全绿。此前完整玩法测试曾有四项失败，未因入口测试通过而解决。不要把入口回归数量包装为全项目质量结论。

## 13. 性能测量要写清范围

同截图、缓存预热、三次中位数，只有knowledge阶段：
- 地图详情563.8ms → 65.7ms。
- 现场交互568.7ms → 13.2ms。
- 明确对话547.5ms → 约0ms，因为跳过扫描。

这些数据早于后续蒙版和设施多尺度变更，不是当前版本所有状态的保证。截图、结构识别、输入、动画等待和OCR都要计入端到端耗时。未来应另测冷启动、恢复搜索和实机卡顿。

优化次序通常是：减少无关工作 → 缩小搜索区域 → 缓存资产 → 最后考虑并行。控制输入保持单一所有者；不能为了并行把过期截图和新动作混在一起。

## 14. 下一轮的实际优先级

- 用新运行trace检查地图整理、通用对话和入口成功交接是否可靠。
- 增加失败现场截图缓冲，减少纯文字盲排查。
- 把状态输出、置信证据与模块返回字段进一步统一。
- 将成熟的共享识别逐个接入每日模块，不影响独立玩法。
- 完善菜单/通知等覆盖层证据，避免“自由HUD可见”过度泛化。
- 视角标定、连续移动与小地图导航按独立设计推进。

核心工作习惯：先描述可观察事实，再执行有限动作，用新证据确认结果；记录经验时同时记录边界、失败样本和验证等级。
