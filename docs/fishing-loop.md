# 钓鱼循环决策树（0.1.0）

用户确认：每次钓鱼结束后，右下角点击“继续”会开始新一轮等待。本组件只实现这个循环，不换饵、开图鉴或领奖。实时控制沿用已调好的钓鱼组件和当前配置，不改变惯性控制参数。

## 启动

手动进入钓鱼轨道后：`run_fishing_loop.cmd --live`

已经抛竿且在等鱼时：`run_fishing_loop.cmd --phase waiting --live`

限制5轮：`run_fishing_loop.cmd --live --max-rounds 5`

默认不带--live只判断，不点击继续；只判断时也不会假定点击成功并虚构下一轮。默认auto只从已识别的轨道、TAP!或继续页接管。普通等待画面无法可靠识别时，使用显式--phase waiting。留3秒切回游戏。F12或Ctrl+C停止。

默认最多999个实时组件调用，整段超时100小时（360000秒），每个实时阶段仍保留原180秒上限。达到轮数上限时停在最后结算页，不再点击继续；max_rounds是调用轮数上限，不代表成功钓获数。

## 调用链

顶层Agent→use_skill fishing_loop（domain hololive_dreams）→领域FishingLoop→run_fishing（waiting/control）→局部继续识别→点击一次→验证离开结算→下一轮waiting。

顶层先完整full观察，再复核前台窗口和当前局部状态。决策树独占操作；每帧实时控制不调用顶层或OCR。一次顶层任务不能重复接管钓鱼组件；返回后由顶层处理具体原因。旧fishing_assist单轮入口保留。

Python入口：src/modular_agent/realtime/fishing_loop.py中的run_fishing_loop(root, computer, handle, live=False, phase='auto', max_rounds=999, timeout=360000, should_yield=..., progress=...)。领域树在domains/hololive_dreams/models/fishing_loop.py，依赖注入observe/realtime/click_continue便于以后增加钓鱼策略。策略范围目前仅继续下一轮。

## 结算识别与反馈

实时组件返回track_lost_result_pending后释放输入，决策树在右下角ROI运行OCR，不运行UIA或全屏模板匹配。仅接受高置信度、唯一的“继续”或“点击继续”，连续两次位置稳定后再次获取新画面复核，再点击文字中心。坐标来自当前帧，按普通左键不加Alt。

钓鱼配置中的continue_roi默认[0.60,0.65,1,1]，相对于游戏客户区，格式[left,top,right,bottom]，可按实际页面调整。缺少实际结算截图，因此这一区域与OCR识别尚未实机验证。若文字无法识别，停在settlement_unknown；不会按固定坐标点击。

点击后最多8秒等待继续页消失；已识别轨道可直接恢复control，TAP!恢复waiting；两次继续标签消失后按用户规则进入waiting。消失只确认页面转换，不能证明钓鱼成功。按钮一直存在则continue_not_dismissed，不连续点击；结算未知超过12秒、失焦、缩放、异常、取消均停止释放。

outcome保持unknown、verified=False；记录rounds、continue_clicks和confirmed_transitions，不以轨道消失或继续点击统计成功。换饵、图鉴和领奖仍交给其他模块。

runtime/fishing/loop-result.json保存循环返回与每轮实时耗时统计；无法识别继续时保存last-boundary.png局部截图，方便校准。单轮旧last-result.json继续保存最近一轮数据。

## 验证

合成两轮链路、结算未知、按钮变化、点击无反馈、异常释放、停止、只判断不输入、当前帧坐标和无需Alt、顶层full复核及禁止重复接管均有测试。现有两张截图验证实时识别；尚未拿到真实继续页，不能声称循环已经实机成功。

## 未知页有限恢复（2026-10-03）

初始未知页或实时结束后结算识别超时，可在本地尝试恢复：优先找右上方/弹窗右侧的独立X、×或“关闭”，其次识别“继续/点击继续”；仍找不到时点击游戏客户区中央。识别按钮需两帧稳定，点击前再次核对窗口。每次点击后重新识别；本次循环最多30次恢复操作，中央最多10次，同一次恢复不重复点未消失的同一按钮。只判断模式记录拟执行动作而不输入。

恢复阶段允许游戏客户区OCR，不进入每帧实时循环；先检查轨道和TAP!，防止恢复时点到正在进行的实时阶段。失焦、缩放、取消、输入失败不做恢复，仍立即释放交回。X为OCR文字识别，未必能识别纯图标关闭按钮；没识别到时按用户授权尝试中央一次。恢复动作记录在loop-result.json的recovery_actions中。顶层初始接管仍要求可识别钓鱼界面，运行中未知页可恢复；独立auto入口也支持初始未知页有限恢复。

当前恢复上限：每次未知页最多30次恢复尝试，其中屏幕中央最多10次；恢复后会重新检测control、TAP或waiting状态，避免恢复成功后立即退出。

## 继续点击未响应时重新点击（2026-10-07）

普通结算识别已接入橙色继续按钮CV，不只在未知页恢复中使用。移动到目标后等待80ms，按住左键120ms再独立松开，避免原30ms短点击没有响应。每次重试均重新识别和复核窗口、目标位置；每次点击至少间隔1秒，一轮过渡检查最多点击5次。

按钮仍在时不能转入waiting或增加confirmed_transitions。5次未响应时返回结算识别流程，继续观察和重试，受总轮数/100小时时长和F12停止控制。确认轨道或TAP可直接切换；继续按钮已不见且同一窗口连续两轮未知才切回waiting。后一规则只表示页面转换，不证明钓鱼成功。取消、失焦、输入异常仍释放所有输入。

新增回归覆盖首点未响应后二次点击成功、按钮始终存在不进入waiting、取消时停止重试、120ms按住后的独立释放，以及用户奖励截图在普通结算观察路径直接命中继续按钮。实机是否有效仍需验证。


等待状态防卡住：循环入口为实时组件提供每秒一次的边界检查，仅采集游戏客户区右侧 40%，使用局部 CV 检测继续和关闭按钮，不启动 OCR/UIA。发现按钮立即释放输入并交回决策树；继续按钮重新确认后重试点击，边界返回不计作完成一轮。控制状态不执行该检查。结果记录 boundary_probe_count 和 boundary_probe_mean_ms。单独运行实时组件的默认行为不变。

关闭按钮识别必须验证蓝色圆圈内部的 X 字形，并支持尺寸变化；仅有蓝色圆圈或返回箭头不能触发关闭恢复。正常等待画面的返回箭头已加入离线回归样本。

图鉴奖励弹层：等待期间另采集底部中央小区域，以“点击关闭”文字模板识别 dismiss 状态；交回决策树后确认位置并点击该提示，重新识别后续页面。适用重试上限与其他恢复按钮相同，不把点击关闭当作继续进入等待。

图鉴 X 的蓝色外圈可能与背景相连；识别保留内部轮廓并单独匹配 X 字形。常规边界识别直接返回确认的 close 状态，恢复流程优先处理此结果，不依赖 OCR 成功后再检测 X。
